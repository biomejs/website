## Markdown support

<Picture src={deckMd} formats={['avif', 'webp']} alt="Biome mascot with a deck of card. The Markdown card is highlighted" />

Biome now support Markdown. The vast majority of the parser was implemented by <Contributor handle="jfmcdowell" />, who implemented the whole parser, the testing suite, the testing suite, and a great harness that makes sure the HTML generated by our parser complies with CommonMark. The parser has 100% CommonMark conformance coverage. Thank you for your great contribution!

The Markdown formatter has a level of Prettier compatibility of ~92%, and we believe the compatibility will be higher in real-world projects. The parser support **GitHub Flavored** extensions such as task items, tables and short links by default. The frontmatter support can be enabled via `markdown.frontmatter` option.

When the frontmatter is enabled, Biome will parse, format and lint the YAML portion of the file.

Fenced code blocks will be automatically formatted if the language of the snippet is recognised and supported by Biome. In the following example, Biome understands that the code snippet uses JavaScript, so it will format it accordingly.

````md title="file.md" ins="js" ins={5} del={4}
Example:

```js
const foo = 'bar'
const foo = "bar";
```
````

## Biome plugins enhancements

<Picture src={deckJs} formats={['avif', 'webp']} alt="Biome mascot with a deck of card. The JavaScript card is highlighted" />

With the combined efforts of <Avatar handle="siketyan" /> and <Avatar handle="ematipico" />, Biome v2.6 now offers new capabilities for plugins.

### JavaScript plugins

It took us a lot to achieve this milestone, but we're excited to announce that JavaScript plugins in Biome are now available as **developer preview**, and you can start creating and shipping custom lint rules.

We built Biome plugins to reflect as much as possible the architecture, shape and APIs used in Rust, so you'll get a sense of how you can create lint rules in Biome. Here's an example of how a Biome JavaScript looks like:

```js title="plugin.js"
import { ast, defineRule, registerDiagnostic } from "@biomejs/runtime/plugin";

const RESTRICTED = new Set(["eval", "setTimeout", "setInterval"]);

export const restrictedCallee = defineRule({
	query: ast("JS_CALL_EXPRESSION"),
	run(node) {
		const callee = node.callee;
		if (callee?.kind !== "JS_IDENTIFIER_EXPRESSION") return;
		if (!RESTRICTED.has(callee.text)) return;
		registerDiagnostic(callee, "error", "Restricted callee");
	},
});
```

Then add the plugin to your configuration file:

```json title="biome.json" ins="plugin.js"
{
  "plugins": [
    "plugin.js"
  ]
}
```
There are some particular characteristics about Biome plugins worth mentioning:
- You can use `.js` files, or `.ts` files. Both are valid file extensions as plugins. Under the hood, Biome strips the types during the loading phase, and the files are eventually loaded as JavaScript files. This is the same strategy adopted by Node.js.
- Biome uses the CST (Concrete Syntax Language), a particular form of syntax tree that stores all the information of a program. Working with a CST can be tedious and verbose, but it provides higher control because you can read all tokens (keywords, strings, comments, etc.).
- Biome is a error-resilient parser, which means that is able to format and lint a program with syntax errors. The recovery mechanism from syntax error depends on the parser, and then the parser recovers, Biome uses "bogus" nodes to decorate the invalid code. While navigating the CST nodes, you'll have access to these bogus nodes. You can decide to ignore them, or attempt to visit them. This is a complete different model from other plugin systems such as ESLint, Prettier, Stylelint, oxlint, etc. so we encourage you to take your time, and get familiar with this new model.
- JavaScript plugins tap directly from our Rust infrastructure, which means they have access to a lot of information such as semantic model, control flow graph, file name, package manifest, module graph, type inference, and more. However, for this release, we intentionally decided to expose a subset of services. We see a lot of potential, however this is also uncharged ground for us too, so we need your [feedback](https://github.com/biomejs/biome/issues/11420) to build a good foundation.

Under the hood, Biome plugins use a JavaScript runtime built in Rust called [`boa`](https://boajs.dev/). Boa is a very promising and upcoming project. The team are the authors of [`temporal_rs`](https://boajs.dev/blog/2025/09/24/temporal-release), the engine that powers the new [`Temporal`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Temporal) APIs of V8 and Node.js.

Refer to the [relative guide](/linter/plugins#javascript-plugins) to learn about how they work, and the APIs at your disposal.

### Plugin distribution

You can now distribute configuration files, GritQL plugins and JavaScript plugins altogether using a npm package. At the root of you package create a `biome-manifest.json` file, and use it share opinionated configuration files, GritQL plugins, JavaScript plugins and rule presets.

Additionally, the new system allows you to import other Biome packages and distribute them under the umbrella of your package. This system is usually called aliasing.

Here's an example of how `biome-manifest.json` could look like. The example exposes the following:
- Via `configs`, two configuration files, one called `strict` and one called `recommended`.
- Via `plugins`, two lint rules, one called `useCompanyLogger` implemented in JavaScript, one called `noLegacyLibrary` implemented in GritQL.
- Via `plugins`, two presets, one called `recommended`, which enabled the rule `useCompanyLogger`, and one called `strict` which enables the rules `useCompanyLogger` and `noLegacyLibrary`

```json title="biome-manifest.json"
{
  "version": 1,
  "configs": [
    { "recommended": "./configs/recommended.json" },
    { "strict": "./configs/strict.json" }
  ],
  "plugins": {
    "rules": [
      { "useCompanyLogger": "./rules/useCompanyLogger.js" },
      { "noLegacyLibrary": "./rules/noLegacyLibrary.gri" }
    ],
    "presets": {
      "recommended": ["useCompanyLogger"],
      "strict": ["useCompanyLogger", "noLegacyLibrary"]
    }
  }
}
```

Then, in the `biome.json`, you can consume presets, configuration, and rules. In the following example, `configs/strict` and `presets/strict` are enabled, assuming your package is called `@org/biome-plugin`:

```json tilte="biome.json" ins="configs/strict" ins="presets/strict"
{
  "extends": ["@org/biome-plugin/configs/strict"],
  "plugins": ["@org/biome-plugin/presets/strict"]
}
```

Refer to the [relative guide](/guides/publish-packages) to learn more about what you can publish, and how the users can consume your packages.

You can still distribute your configuration file using the old way, but it's now considered legacy.

### Resolve plugins relative to shared configurations

Biome 2.6 introduces the `resolutionKind` option for object-syntax plugin entries, making plugins easier to reuse from shared configurations.

By default, Biome resolves plugin paths in a shared configuration from the directory containing the configuration that extends it. To load a plugin that ships with the shared configuration, set `resolutionKind` to `"config"`:

```json title="biome.shared.jsonc"
{
  "plugins": [
    {
      "path": "./plugins/no-object-assign.grit",
      "resolutionKind": "config"
    }
  ]
}
```

Then extend the shared configuration:

```json title="biome.json"
{
  "extends": ["./biome.shared.jsonc"]
}
```

Biome resolves the plugin path from the directory containing `biome.shared.jsonc`, while `includes` globs are still resolved from the directory containing the extending configuration.

See [`plugins.<ITEM>.resolutionKind`](/reference/configuration#pluginsitemresolutionkind) for the full option reference.

Thank you <Contributor handle="soconnor-seeq" /> for contributing this feature.

## Better Tailwind CSS integration

<Picture src={deckTw} formats={['avif', 'webp']} alt="Biome mascot with a deck of cards. The Tailwind card is highlighted" />

Biome 2.6 brings Tailwind-aware linting and class sorting closer to the way developers like to use Tailwind in their projects.

In patches leading up to this release, we've improved our Tailwind parser and expanded Tailwind class detection across HTML, Vue, Svelte, and Astro, and introduced new rules like [`useTailwindShorthandClasses`](https://biomejs.dev/linter/rules/use-tailwind-shorthand-classes/) and [`noTailwindRawColors`](https://biomejs.dev/linter/rules/no-tailwind-raw-colors/). After lots of testing and fixing many bugs, we're finally ready to really close the gap on our native Tailwind support.

We've revamped class sorting and added new rules inspired by [`@shadcn/lint`](https://github.com/shadcn-ui/lint) designed to make agents produce high quality, idiomatic Tailwind styles. We're excited for you to try them out and to listen to your feedback as we continue iterating on them.

### Tailwind CSS v4-aware sorting and stylesheet configuration

You've been waiting for this one for a long time, and it's long overdue. We're excited to finally ship Tailwind class sorting, one of our oldest and most requested features (460 👍 reactions)! The nursery rule [`useTailwindSortedClasses`](https://biomejs.dev/linter/rules/use-tailwind-sorted-classes/) (formerly `useSortedClasses`), has been updated to the sorting semantics of Tailwind v4.

:::caution[Sorting behavior changed]
Previously, the rule sorted classes based on Tailwind v3 semantics. The rule has been overhauled to align with Tailwind v4, and the sorting behavior is now significantly different than it was before.
:::

Tailwind v4 introduced "design systems", where you define your application's appearance as variables in CSS, and those automatically become available as Tailwind classes. Biome is now able to read this configuration stylesheet and it takes your design system into account when sorting classes.

```jsonc title="biome.jsonc"
{
  "tailwind": {
    "stylesheet": "app/global.css"
  }
}
```

Thanks to <Contributor handle="johncarmack1984" /> for the help with the sorting implementation, and <Avatar handle="dyc3" /> for working on the Tailwind parser!

### `noTailwindRawColors`

Your design system probably defines a small set of colors to use, and where to use them. How many times have you told your agent something like "make the danger button red", and it does something silly like this:

```jsx
<button class="bg-red-500">Danger</button>
```

You might even have a skill that tells the agent not to do that, but maybe it decided not to read it. Frustrating, right? You wanted it to use the `--color-danger` you have defined in your config.

In case you missed its debut in 2.5.15, [`noTailwindRawColors`](https://biomejs.dev/linter/rules/no-tailwind-raw-colors/) inspired by [`no-raw-colors`](https://github.com/shadcn-ui/lint/blob/main/docs/rules/no-raw-colors.md), flags these cases, and points you or your agent to your design system's existing colors.

```jsx
<button class="bg-danger">Danger</button>
```

### `noTailwindRestyledComponents`

Many of you have your own component library to keep your application's visual style consistent. Not just the colors, but the whitespace, borders, font size, and animations are all the little things that make your user experience consistent and beautiful. That consistency crumbles when your agent forces new styles on your components.

```jsx
// The Button's styles are overridden
<Button className="bg-red-500 text-white rounded-none" />;
```

The new nursery rule [`noTailwindRestyledComponents`](https://biomejs.dev/linter/rules/no-tailwind-restyled-components/), inspired by [`no-restyle`](https://github.com/shadcn-ui/lint/blob/main/docs/rules/no-restyle.md), reports utilities that change a component's color, typography, spacing, shape, effects, or motion.

```jsx
// Use the variant the design system provides instead
<Button variant="danger" />;
```

You can also add exceptions, which can help with adopting this rule:

```json title="biome.json"
{
  "linter": {
    "rules": {
      "nursery": {
        "noTailwindRestyledComponents": {
          "level": "error",
          "options": {
            "allow": [
              { "components": ["Card"], "categories": ["spacing"] },
              { "components": ["Button"], "classes": ["hover:shadow-lg"] }
            ]
          }
        }
      }
    }
  }
}
```

### `useTailwindStaticClassStrings`

Tailwind relies on string matching in order to detect tailwind classes. It scans your source code for the exact class strings, and only emits CSS for the matches. Without proper guidance, agents have a tendency to dynamically construct tailwind class strings. This causes the styles to be missing from your build output.

```jsx
// Tailwind can't see the class!
<div className={`bg-${color}`} />;
```

The new nursery rule [`useTailwindStaticClassStrings`](https://biomejs.dev/linter/rules/use-tailwind-static-class-strings/), inspired by [`require-static-classes`](https://github.com/shadcn-ui/lint/blob/main/docs/rules/require-static-classes.md), flags dyanmically built strings used to build class strings. It encourages using merge functions like `clsx` and `cn` instead.

```jsx
<div className={active ? "bg-red-500" : "bg-blue-500"} />;
<div className={clsx(active && "bg-red-500", "text-white")} />;
```

### Tailwind class detection

All Tailwind rules will detect class strings in the exact same way, across JSX, TSX, HTML, Vue, Svelte and Astro files. The default settings should work out of the box for the majority of users, but you can configure how Biome detects class strings with the new `tailwind` top-level configuration:

```jsonc title="biome.jsonc"
{
  "tailwind": {
    "mergeFunctions": ["clsx", "cn", "twMerge"],
    "variantFunctions": ["cva", "tv"],
    "attributes": ["class", "className"]
  }
}
```

## The new `biome inspect` command

The new command `biome inspect` is the first step towards having better debugging tooling for both maintainers and users.

### `biome inspect config`

This command allows you to inspect the whole configuration or single values inside your project. What's powerful about is that this command is able to resolve extended configurations via `extends`, path `overrides`, configuration files inside monorepos, and you can also inspect single fields using the dot-notation style.

You can start by running the default command from the root of your project, and you'll receive the final representation of your configuration file:

```shell
biome inspect config
```

```text
biome.jsonc configuration ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  i Resolved configuration from biome.jsonc.

  Configuration files used (merge order):
    - biome.jsonc

  {
    "formatter": {
      "lineWidth": 100
    },
    "overrides": [
      {
        "formatter": {
          "lineWidth": 120
        },
        "includes": [
          "**/*.test.js"
        ]
      }
    ]
  }

  i Overrides are included but were not evaluated because no --path was provided.
```

If you need to evaluate `overrides`, you must provide a `--path` to a file.

```shell
biome inspect config --path ./src/components
```

You can also inspect portions of the configuration file, or fields, using the dot-notation style. To inspect arrays, you must provide a number. Here's a few examples:

```shell
biome inspect config formatter # inspect the whole "formatter" object
biome inspect config formatter.lineWidth # inspect the "formatter.lineWidth" field
biome inspect config linter.rules.suspicious.noDebugger # inspect a lint rule
biome inspect config plugins.1 # inspect the first item in the "plugins" array
```

### `biome inspect plugins`

This command resolves all the plugins loaded by your project, and list all the rules that are enabled in your configuration file. This is useful if you use multiple plugins and you enable rules via presets, so it provides you with e clear list of all rules.

The command also shows if rules were improved from a local source (your project) or an external source (an npm package). Here's an example of the output:

```txt

  i The configuration enables 4 plugin rules for src/app.test.ts.

  @acme/accessibility

  - noAutofocus (listed directly, presets/recommended)
  - noPositiveTabindex (presets/recommended)
  - noRedundantRoles (presets/recommended)

  @acme/javascript

  - noAlert (presets/recommended, presets/strict)

  @acme/security

  - noDocumentWrite (presets/recommended)

  @acme/testing

  - expectExpect (listed directly, presets/recommended, presets/strict)
  - noConditionalExpect (presets/recommended, presets/strict)
```

### `biome inspect file`

This command shows debugging information for a file, such as CST, typed CST, formatter IR, Semantic Mode (if available), given a certain file. We think this command might come in handy if you write a plugin, and you need to look at the shape of the CST without looking at the playground. The command must accept a path to a file:

```shell
biome inspect file path/to/file.ts
```

### Recursive configuration inheritance

Biome v2.6 now allows you to extend configuration files and plugins from many ancestors. We still have an hardcoded limit in place of ten levels of depth to avoid possible overflows or cycles. This means that external packages can use `extends` from external packages, and so on. The end user just need to consume the file configuration file, or plugin.

## Migrate from Stylelint

With this update, we added a migration path from Stylelint.
Biome can now automatically migrate your existing Stylelint configuration using the following subcommand:

```shell
biome migrate stylelint --write
```

This command will read your Stylelint configuration and attempt to port their settings to Biome.
Porting rules, overrides and ignore patterns from both the `ignoreFiles` key in the configuration & the `.stylelintignore` file.

Given the following Stylelint configuration:

```json title=".stylelintrc.json"
{
	"ignoreFiles": ["dist/**"],
	"rules": {
		"block-no-empty": true,
		"font-family-no-duplicate-names": true,
		"keyframe-declaration-no-important": true
	},
	"overrides": [
		{
			"files": ["*.scss"],
			"rules": {
				"block-no-empty": null
			}
		}
	]
}
```

Running `biome migrate stylelint --write` will produce the following `biome.json`:

<Code title="biome.json" lang="json" code={`{
    "$schema": "https://biomejs.dev/schemas/2.6.0/schema.json",
    "vcs": { "enabled": false, "clientKind": "git", "useIgnoreFile": false },
    "files": { "ignoreUnknown": false },
    "formatter": { "enabled": true, "indentStyle": "tab" },
    "linter": {
      "enabled": true,
      "rules": {
        "preset": "none",
        "suspicious": {
          "noDuplicateFontNames": "error",
          "noEmptyBlock": "error",
          "noImportantInKeyframe": "error"
        }
      },
      "includes": ["**", "!dist/**"]
    },
    "javascript": { "formatter": { "quoteStyle": "double" } },
    "overrides": [
      {
        "includes": ["*.scss"],
        "linter": { "rules": { "suspicious": { "noEmptyBlock": "off" } } }
      }
    ],
    "assist": {
      "enabled": true,
      "actions": { "source": { "organizeImports": "on" } }
    }
}`} />

The command needs Node.js to load and follows `extends` and plugin configurations.
For now, `biome migrate stylelint` only supports Stylelint configurations written in JSON or JavaScript. YAML configurations are not supported yet.

By default, the command migrates identical rules only. Pass the `--include-inspired` flag to migrate inspired rules as well.
